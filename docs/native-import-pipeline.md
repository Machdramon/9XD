# Native containers and geometry patterns

9XD can inspect supported archive/compression structures without Ollama, Python or an AI service. These stages use the same snapshot reader as Hex Viewer and include pending binary edits.

## Open a contained resource

1. Open a file and use **File Scan**, **Scan for 3D Data**, or **Scan for Textures / Images**.
2. Recognized container entries appear in the results with their names, record offsets, packed sizes and codec.
3. Select an entry and click **Open Resource**. It is read/decompressed in the background and opened as a separate, initially unmodified RAM document. That document is scanned automatically using the same scan mode.
4. Repeat for a nested container, or preview a supported mesh/image. Use Save As if you want a standalone copy of the decoded bytes. Use the normal collection/export tools after validating a mesh.

The parent document is preserved. Archive paths are names, not instructions to write files. No contents are automatically extracted onto disk. A resource records its source chain, sizes, source timestamp where available, pending-edit state and nesting depth in its document provenance. Compressed offsets remain relative to the decoded child; they are not presented as an exact mapping back to packed bytes.

Included container stages:

| Adapter | Current support |
|---|---|
| AFS | Little-endian entry tables, validated ranges; numbered entries. Filename metadata is not yet interpreted |
| ZIP | Single-disk classic ZIP, stored and deflate members; directory/local-name checks, decoded sizes and CRC32. Detection uses headers rather than extensions |
| Gzip | One complete member, including gzip trailer/checksum validation |
| FArC | The observed big-endian table variant with header field 1 and named gzip-compressed entries, tested against the two R-Tuned samples |
| FArc | The observed uncompressed big-endian table variant with header field 1 and named stored entries; tested against STGHKN.farc |

ZIP64, encrypted/multipart ZIPs, concatenated gzip members, other FARC variants (including encrypted variants) and additional codecs are explicitly unsupported. A recognized archive does not establish the format of its children. Container enumeration targets its tables across the file rather than relying on the ordinary 32 MiB metadata prefix.

SEGA text A3DA resources are recognized as animation/camera metadata with external object references. They are not presented as renderable meshes, and animation playback is not implemented. In the supplied R-Tuned cases, the top-level `STGHKN.farc` contains 73 A3DA resources; the separate `course/stghkn.farc` contains the visual geometry, object bindings and textures. The latter exposes a combined static course preview plus optional backdrop/sea and sky groups. See `priority-racing-formats.md` for details and remaining limitations.

Limits: 10,000 entries, 1 MiB FArC table, 8 MiB ZIP directory, 128 MiB packed input and 128 MiB decoded output per opened entry, nesting depth 4. One resource opens at a time per scanner; Cancel stops background work. Large resources and unsupported variants report a reason instead of partially loading as success. Open RAM documents consume memory until closed.

## Geometry-pattern search

The Hex/3D scanners include **Search for possible geometry when no known mesh layout matches**. It is on by default there, off in the image scanner. Known importers/profiles take priority; recognized containers are opened before applying this search to their contents.

The first detector searches the first **8 MiB** for nearby, 4-byte-aligned descriptors containing absolute buffer offset, count and stride, in these field orders:

- offset / count / stride;
- count / offset / stride;
- count / stride / offset.

It tests both byte orders, Float32 XYZ at the beginning of vertex records with strides 12–192, and UInt16/UInt32 triangle-list index buffers described within 256 bytes of the vertex descriptor. It checks bounds, finite coordinates, spatial variation, index ranges and nondegenerate triangles together. There are explicit candidate, descriptor and work budgets.

Results say **Candidate — verify manually**. They never auto-preview and the assistant cannot silently promote them to a confirmed import. Select one to load its settings or preview through the production decoder. Inspect orientation, topology and part boundaries before exporting. Unknown UVs/normals/transforms are disabled, not guessed. Faces are never generated by connecting nearby points.

This initial detector does not cover headerless data, implicit strides, relative pointers, Float16/packed positions, triangle strips, compressed hardware packets, skeletons or arbitrary unknown layouts. An empty result does not establish absence of geometry. Broader patterns are follow-up work driven by the study corpus.

## Developer corpus runner

With `BUILD_TESTING` enabled, CMake builds `native_asset_audit`. It runs the production source reader, container adapters and codecs without starting the GUI or AI:

```text
native_asset_audit <file-or-folder> <report.json> [--verify] [--patterns]
```

`--verify` reads/decompresses supported entries and records errors, decoded sizes and output header samples; no extracted assets are written. Verification is limited to 512 MiB decoded output per source file. `--patterns` records generic geometry hypotheses in unrecognized outer resources. The runner does not recursively decode every child, run all native geometry importers, render, export models or prove visual correctness. Reports include source sizes/timestamps, not full-file cryptographic hashes.

Local validation against the user's 880-file corpus: 222 recognized containers/streams (7 AFS, 4 ZIP, 209 gzip, 2 FArC), 2,862 resources successfully read/decoded, zero codec/range errors. Pattern-only scanning of outer files found zero candidates; six searches hit an internal descriptor/candidate/work cap. These results validate the unpacking stages, not new game-specific geometry support. Synthetic tests validate both byte orders, index rejection, compression corruption/limits, a child beyond the 32 MiB scan window, and archive → new document → candidate → 3D preview.

Next stages: more pointer/attribute/topology patterns, automatic bounded scanning across child resources, reusable container/pipeline profiles, dependency resolution, and per-family geometry/material/texture validation. See `mesh-format-profiles.md` for the existing deterministic geometry profile path.
